## 0. 이번 사용자 요청과 승인 범위

사용자는 기존 게임을 처음부터 다시 만들기로 결정했으며, 개발에 들어가기 전에 다음 다섯 질문을 정확히 검토하고 계획을 기록하라고 요청했다.

1. 기존 자료 외에 더 확보할 방법은 무엇인가? 기술 이펙트·타격감·사운드·아이디 및 캐릭터 생성처럼 어려운 자료는 어떻게 다룰 것인가? 로그인부터 구현된 자료를 구할 수 있는가?
2. 방대한 자료의 중복, 서로 다른 정보, 누락, 오류를 어떻게 정리할 것인가?
3. 확보하고도 활용하지 못하는 자료를 어떻게 처리할 것인가?
4. 한 번에 구축할 것인가, 지도·아이템 등 순서대로 진행할 것인가? 구체적인 개발 순서는 무엇인가?
5. 개발 후 부족함이 쏟아지는 것을 막기 위해 무엇을 사전에 준비할 것인가?

이번에 승인된 작업은 자료·소스 확인, 계획 작성, 기록이다. 게임 코드 수정, 원본 자산 재게시, 서버 실행, 배포, 유료 작업을 시작하라는 승인이 아니다. 재구축 결정은 확정된 사용자 요구이고, 아래 세부 기술·일정 순서는 검토할 실행 제안이다.

기존 문서의 '새 게임 금지, 기존 런타임만 수선'은 이번 재구축 방향에 한해 대체한다. 기존 원본·세이브·브랜치·설치본 보존, 무료 범위, 미실행 PASS 금지 원칙은 유지한다. v2 치명결함 문서의 실패 사례는 새 구현의 회귀시험으로 계승하되 243/05b 코드를 정답으로 강제하지 않는다.

## 1. 고정 목표와 복원 기준

- 목표는 한국판 1998~2001년의 경험을 최대한 충실하게 재현한 개인용 싱글플레이다. 기존 자료와 쓸 만한 기존 도구·코드는 재사용한다. 새 프로젝트라고 모든 파서·저장 코드까지 백지 구현하지 않는다.
- Windows와 Android 휴대폰·Galaxy Tab S10 FE에서 같은 게임 규칙·콘텐츠·저장 형식을 사용한다. Android는 하나의 앱으로 지원한다.
- 로컬 오프라인 플레이를 유지하고, 같은 계정·같은 캐릭터의 기기 간 순차 이어하기 요구를 유지한다. 온라인 접속이 없으면 기존 로컬 캐릭터를 플레이할 수 있어야 한다.
- 기본 화면 기준은 사용자가 제공한 기술·물품·장비 사진 3장이다. 화면 모양의 사용자 지정과 촬영 연도 고증은 구분한다. 오른쪽 상단 물품/기술/장비/능력치 전환, 아래 상태 유지, 한국어 표시를 누락하지 않는다.
- '1998~2001'을 서로 다른 모든 버전을 섞으라는 의미로 사용하지 않는다. 첫 자료 정리에서 기본 도시·직업·성장·UI 기준을 명시한 하나의 복원 프로필을 정한다. 다른 시기 자료는 같은 항목을 교차 검증하거나 빠진 부분을 보완하는 후보로 보존한다.
- 자료가 없는 부분을 영구적으로 비워 두는 것도 목표가 아니다. 확인 자료 → 동시기 교차확인 → 다른 판본의 대응 확인 → 기존 원본의 조합·보간 순서로 보완하고, 재구성 사실은 기록한다.
- 원본 클라이언트의 그림·프레임은 렌더링 근거다. 그것만으로 서버의 몬스터 배치, 경험치, 드롭 확률, 전투 공식까지 확정하지 않는다.
- 한국판 맵을 확보하지 못했다고 북미판 지형에 한국 이름만 붙이고 한국 원본 복원으로 보고하지 않는다.
- 역사적 정확성, 실제 기능 작동, 시청각 유사성, 기기 성능은 서로 다른 판정이다. 등록 수량이나 자가 작성 테스트 통과를 원작 정확성으로 치환하지 않는다.

## 2. 질문 1 — 자료 확보 방법과 어려운 자료의 대응

### 2.1 먼저 '무엇이 부족한가'를 만든다

검색창에 게임 이름만 반복하지 않는다. 기능 목록에 원본 출처와 필요한 증거를 연결하고, 비어 있는 칸을 검색 대상으로 삼는다. 예: 로그인 배경/선택 버튼/전환음, 생성 화면의 머리·색상·성별·선택 순서, 공격 프레임/판정 시점/효과음, 성문별 이동 규칙, 특정 기술의 앞뒤 레이어.

첫 수집에서 전체 범위를 넓게 조사하고, 이후에는 미해결 항목을 대상으로 좁혀 찾는다. 새 사이트 발견 자체보다 필수 기능의 누락을 몇 개 메웠는지를 성과로 기록한다.

기존 확보 파일의 시작 목록: KR_1.25_winbaram.zip, KR_4.91_491v.zip, NA_4.03/4.66/4.95, 구버전 모음, Baram/Judge/Mithia Map Editor, BARAM.PAL, EPF 도구, 타일 아틀라스, Work ASSETS001~003/CONTENT001~010, 기존 연구 브랜치와 UI 참고 이미지. 이전 수량 보고는 인계 단서이고 새 빌드에 실제 포함됐다는 증거가 아니다.

이번 세션에서는 KR1.25/KR4.91/지도도구/아틀라스/243448ac ZIP의 로컬 존재와 이전 v2 문서를 확인했다. 모든 원본 바이트와 파서를 다시 검사한 것은 아니다. 새 작업공간에서는 파일 접근과 SHA 일치부터 확인한다. Library 보관을 Codex 작업공간에서의 파일 접근 가능과 동일하게 취급하지 않는다.

### 2.3 로그인부터 구현한 소스가 있는가?

Project1998의 현재 README는 NexusTK 4.95 대상으로 로그인·캐릭터 생성·월드 진입·전투·기술·상점·퀘스트 등을 지원한다고 설명한다. Architecture에는 LoginServer, 게임 Server, SQLite 상태 저장, LoginProbe가 명시되어 있다.[S1][S2]

따라서 로그인부터의 구현을 관찰하고 재사용할 유력한 코드 기반은 있다. 그러나 이는 북미판 서버 재구현이며, 원하는 시기의 한국판 전체와 Android 오프라인까지 모두 갖춘 검증된 완제품을 확보했다는 뜻은 아니다. 이번에는 문서/구조를 읽었으며 전체 실행시험은 하지 않았다.

우선 기존에 보유한 호환 클라이언트와 함께 참고 실행본으로 검증한다. 계정 생성 → 중복 이름·틀린 비밀번호 등 실패 → 로그인 → 캐릭터 생성 → 진입 → 종료 → 재접속을 구분해서 검사한다. 완성된 기능은 대응 근거가 있으면 재사용하고, 실제 빠진 기능만 새로 구현한다. 새 게임에서 수많은 서버 프로세스·네트워크 의존성을 그대로 가져올 필요는 없다.

한국 원작 로그인 화면의 복원, 로컬 프로필 생성, 여러 기기의 실제 계정 인증은 서로 다른 기능이다. 오프라인 프로필을 서버 인증 성공으로 표시하지 않는다. 기존 요구인 실제 계정 동기화는 초기 단계에서 가능성을 시험하고 후반에 전체 게임에 연결한다.

### 2.4 기술 이펙트·캐릭터 동작

TKViewer는 DAT, DNA, DSC, EPF, FRM, MAP, PAL, 효과/동작/타일/정적 오브젝트 TBL 읽기를 문서화한다. EPFViewer와 TKMapper는 프레임/맵 확인의 보조 후보다.[S3][S4][S5]

이미지 한 장만 추출하지 말고 다음을 하나의 행동 레코드로 묶는다.

`원본 묶음·버전 → 원본 인덱스 → 몸/머리/무기/장비 → 방향 → 행동 → 프레임 순서/지연 → 기준점/앞뒤 레이어 → 팔레트/색상 순환 → 효과 ID → 소리 ID`

정지/걷기/공격/피격/시전/사망 등은 해당 원본에 실제 존재하는 상태부터 확인한다. 존재하지 않는 상태를 모든 캐릭터에 강제 생성하지 않는다. 동일 무기·몸·머리 조합을 네 방향에서 비교하고, 무기와 캐릭터의 좌우가 따로 뒤집히지 않도록 한다.

이펙트마다 시작/반복/종료, 투사체 이동, 범위, 앞/뒤 레이어, 가림, 투명도, 팔레트 변화를 검사한다. 현대식 번쩍임·카메라 흔들림·히트스톱은 근거가 없으면 추가하지 않는다.

### 2.5 사운드와 타격감

소리 파일만 찾아서는 충분하지 않다. 파일 ID·길이·반복 구간·채널·볼륨·호출 조건과 행동의 재생 시점을 함께 연결한다. 포맷별 디코더를 확인하고 원본 샘플레이트와 변환 이력을 보존한다. 만약 MIDI가 있다면 연주 데이터와 음원/사운드폰트 차이를 구별한다.

타격감은 다음 시간축으로 기록한다.

`입력 수신 → 동작 시작 → 공격 유효 프레임 → 명중/피격 표시 → 소리 출력 → 다음 이동·공격 허용`

프레임 캡처, 이벤트 로그, 녹음 파형을 비교한다. 서버 통신 지연·영상 프레임 누락·녹화 속도·오디오 출력 지연은 애니메이션 자체의 시간과 분리한다. 한 스크린샷에서 타격 시간이나 드롭 확률을 추정하지 않는다. Godot도 재생 요청과 실제 오디오 출력의 지연을 구분하므로 play() 호출 로그만으로 청각 검증 PASS 금지.[S6]

원본 재생 → 새 구현을 같은 조건으로 나란히 비교한다. 계측 가능한 차이와 '기억하는 느낌'을 나누고, 사용자의 체험 평가는 최종 감각 조정에 사용한다. 사용자를 매번 오류 탐색 담당자로 만들지 않는다.

### 2.6 끝내 못 구한 자료

순서는 원본 교체 확보 → 기존 다른 파서로 교차해독 → 같은 계열/시대의 대응 자료 → 영상/문서로 제약한 재구성 → 명시적인 임시 보완이다. 원본이 없는 프레임은 확보된 같은 캐릭터·팔레트·동작으로 최소 보완하며 다른 게임 스타일로 만들지 않는다. 소리 분리·영상 복원·추가 프레임 생성 결과는 복원/가공 자료로 표기한다.

필수 기능의 동작은 만들되 '작동한다'와 '원작과 동일하다'를 구분한다. 상위 기술 이펙트 한 개가 미확인이라는 이유로 전체 개발을 멈추지 않는다. 반대로 한국 기본 지형·캐릭터 합성·저장 같은 기초가 입증되지 않았는데 대규모 콘텐츠 제작으로 넘어가지 않는다.

수집 종료 조건: 다음 개발 단계에 필요한 기본 자료가 확보되었고, 우선 출처들을 재확인해도 새로 해결되는 항목이 거의 없으면 자료 세대를 동결한다. 미해결 목록은 남겨 두고 개발과 병행해 목표 검색을 계속한다. '인터넷 전체를 다 찾은 뒤 시작'은 하지 않는다. 새 자료는 현재 세대에 몰래 덮어쓰지 않고 다음 후보 변경으로 검토한다.

## 3. 질문 2 — 방대한 자료의 정리와 충돌 처리

### 3.1 네 층, 하나의 관리 기준

1. 원본: 받은 파일·압축·문서를 바이트 그대로 보존한다.
2. 추출본: 파서별 출력과 원본 위치를 남긴다. 오류 파일은 별도 격리한다.
3. 채택 자료: 현재 복원 프로필에서 선택한 지도·수치·외형·동작을 유지한다.
4. 실행 패키지: 검증된 채택 자료를 자동 변환한 읽기 전용 묶음이다. 수작업 수정 금지.

검색 색인은 SQLite 같은 경량 저장소 하나로 시작하고, 사람이 읽는 JSON/CSV 내보내기를 지원한다. 원본·추출 파일은 파일시스템에 보관하고 색인에 중복 넣지 않는다. 벡터 DB·외부 유료 AI·상시 서버를 자료 정리의 필수조건으로 만들지 않는다. 실행 게임은 조사 DB 전체가 아니라 필요한 실행 패키지만 읽는다.

### 3.2 필수 메타데이터

자료마다 `source_id, game_region, client_build, content_era, captured_at, source_path_or_url, sha256, archive_member, original_id, parser_version, observed_or_inferred, notes`를 기록한다. 버전을 모르면 UNKNOWN으로 남긴다.

게임 항목에는 안정적인 `content_id`를 따로 부여한다. 아이템명·지도명은 바뀔 수 있으므로 ID로 사용하지 않는다. 같은 원본 숫자 ID라도 지역·버전이 다르면 다른 항목으로 간주하고 대응표에서 합친다. 원본명·한국어 표시명도 분리한다.

출처는 레코드 하나가 아니라 필드별로 추적한다. 예: 한 아이템의 아이콘은 한국 클라이언트, 가격은 당시 설명서, 착용 조건은 공략, 공격 공식은 별도 관찰에서 올 수 있다.

### 3.3 겹치거나 다른 정보

- 바이트가 같은 파일: 저장은 중복 제거하되 발견 출처는 모두 보존.
- 같은 그림·다른 팔레트: 무조건 중복으로 삭제하지 않고 색상 변형 관계 유지.
- 같은 이름·다른 연도/지역/직업/등급: 별도 판본으로 보존. 이름 일치만으로 합치지 않음.
- 같은 항목·다른 값: 조건과 출처 계보를 먼저 확인. 복제한 사이트/포크 여러 개를 독립 근거 여러 개로 세지 않음.
- 손상·해독 실패·글자 깨짐: 원본 손상인지 포맷/CP949·EUC-KR·UTF-8 처리 오류인지 구분. 복구본은 원본과 다른 새 버전으로 보존.
- AI 생성/추론 데이터: 원본 출처와 구별하며, 이전 AI 보고서의 PASS는 새 원작 근거로 사용하지 않음.

출처를 하나의 전역 신뢰도 숫자로 정렬하지 않는다. 그림에는 실제 클라이언트가 강하지만, 서버 배치/확률에는 클라이언트 그림이 답이 아니다. 해당 필드의 지역·시기·측정 조건이 맞는 근거를 우선한다. Project1998 역시 RTK의 후대 자료와 밸런스 차이를 경고하고 있다.[S7]

이전에 이야기한 평균·반올림은 동일 버전·동일 조건의 비교 가능한 계측치에만 제한한다. 한국/북미, 1998/후대, 일반몹/보스, 기본/버프 상태가 다른 숫자를 평균 내서 가상의 원작값을 만들지 않는다. 원본 팔레트 두 개의 색을 무조건 중간색으로 바꾸지 않는다.

채택할 수 없는 충돌은 후보 A/B와 미해결 이유를 남기고, 플레이를 위한 잠정값을 쓰면 그렇게 표시한다. 정답 자료가 오면 해당 데이터만 교체할 수 있게 한다.

### 3.4 판정 축 분리

- 사실성: ORIGINAL_VERIFIED / CORROBORATED_RECONSTRUCTION / INFERRED / UNKNOWN.
- 이용 상태: DISCOVERED / ACQUIRED / DECODED / IDENTIFIED / BOUND / EXERCISED.
- 시험 결과: PASS / FAIL / NOT_RUN / BLOCKED, 시험한 환경·커밋·출처와 함께 기록.

제작자의 README 주장은 DOCUMENTED_CLAIM이다. 테스트 미실행 상태에서 실행 검증으로 승격하지 않는다.

## 4. 질문 3 — 확보하고도 활용 못하는 문제의 해결

### 4.1 '보유 자산'이 아니라 '자료에서 플레이까지'를 추적

각 필수 콘텐츠에 다음 연결표를 만든다.

`원본 파일/인덱스 → 파서 출력 → 안정 ID → 원본 의미 식별 → 실행 참조 → 필요한 기능 → 실제 화면/소리/게임 결과 → 증거`

아이콘 파일이 존재해도 가방에서 그리는 호출이 없으면 BOUND 또는 EXERCISED가 아니다. 기술 ID가 있어도 효과·소리·학습 조건이 없으면 완성 기술이 아니다.

### 4.2 미활용 사유를 행동으로 바꾼다

| 미활용 원인 | 다음 조치 |
|---|---|
| 작업공간에서 파일을 읽을 수 없음 | 실제 바이트 전달과 SHA 대조. 목록만 보고 확보 완료 금지 |
| 압축·포맷 해독 실패 | 컨테이너/버전별 기존 파서 비교, 최소 실패 샘플로 단위시험 |
| 해독했지만 이름/ID/색상 의미 모름 | 원본 시트·동작 표·영상·다른 버전 대응을 나란히 확인 |
| 자료는 연결됐으나 지원 코드 없음 | 필요한 효과 명령/서비스/상태를 구현. 지원 불가 명령은 빌드 오류 |
| 코드에서 참조하지만 패키지 누락 | 실행 패키지의 의존 관계와 manifest를 검사 |
| 업데이트해도 옛 모습 | 입력 파일+변환 코드+설정+형식 버전 해시로 캐시 무효화 |
| 지금 모드에서 쓰지 않는 타시대 자료 | 의도적 미사용으로 보관. 재현도를 해치는 억지 삽입 금지 |

### 4.3 자료 검수 화면은 한 번만 만든다

새 게임과 같은 실제 렌더러를 쓰는 개발용 검수 장면을 둔다. 맵+충돌+출구+스폰, 캐릭터 몸/머리/무기/장비+네 방향, 아이템 아이콘, 기술 애니메이션+소리를 한곳에서 조회한다. 원본 ID와 실행 ID를 함께 표시하고 스크린샷·행동 로그를 남긴다. 별도 웹서비스나 두 번째 게임을 만들지 않는다.

원본 파서 검증에는 다른 도구/영상 등 독립 근거도 사용한다. 검수 장면과 게임이 같은 잘못된 파서를 공유하면서 서로 일치했다고 정확성을 확정하지 않는다.

### 4.4 모든 원본을 저장하되 모두 활성화하지 않는다

목표는 원본 파일의 분류 누락 0, 현재 필수 콘텐츠의 미연결 0, 의도적 미사용 사유 누락 0이다. 중복·다른 시대 자료까지 100% 게임에 집어넣는 것이 목표가 아니다.

등록, 실제 로드, 도달 가능, 시청각 확인, 정상 플레이 확인의 수를 각각 보고한다. 도달성은 캐릭터 레벨·전직·퀘스트 등 정상 조건을 반영한다. 모든 맵이 레벨1에게 열려야 한다는 검사는 하지 않는다.

기준 실행 패키지의 필수 맵/효과/소리/아이콘이 빠졌으면 조용히 다른 것으로 대체하지 않는다. 오류 항목을 식별하고 새 후보 배포를 막는다. 기존 정상 설치본과 세이브는 보존한다.

## 5. 질문 4 — 개발 순서

### 5.1 방식: 전체 설계, 작은 종단 연결, 대량 확장

맵 전체를 만들고 한참 뒤 전투를 붙이는 분리형 개발도, 모든 기능을 한 번에 생성하는 방식도 채택하지 않는다. 먼저 전체 필요한 기능과 데이터 계약을 정한다. 그 다음 '게임을 켜서 플레이하고 저장 후 재진입하는 실제 한 구간'을 만든 뒤 검증한 방식으로 나머지를 일괄 확장한다.

자료 수집/해독/전수 목록은 넓게 병렬 진행한다. 게임 코드는 하나의 통합 책임자가 기준 브랜치에 반영한다. 맵마다 AI가 장시간 같은 수동 플레이를 반복하지 않고 전수 자동검사와 대표/예외 시각 검사를 결합한다. 장시간 자연 육성 평가는 전체 통합 뒤 집중한다. 단 최초 작동 검증과 기능 변경별 짧은 회귀시험은 끝으로 미루지 않는다.

### 5.2 단계표

| 단계 | 작업 | 다음 단계로 가기 위한 산출물 |
|---|---|---|
| P0 보존·범위 | 기존 코드·자료·세이브·설치본 및 결함 기록 보존. 새 게임 범위·UI·온라인/오프라인 의미·제외 항목 확정 | 요구-자료-기능-시험 연결표, 기존 원본 위치/해시 |
| P1 확보·정리 | 위 다섯 경로 조사, 기존 원본 전수 목록, 필드별 충돌·누락 분류, 복원 프로필 설정 | 자료 카탈로그, 채택 규칙, 우선 미해결 목록 |
| P2 위험 기술 검증 | 기준 클라이언트 로그인/생성 확인; 한국 원본 맵 해독·캐릭터 합성·효과+소리; Windows/Android에서 같은 작은 장면·입력·로컬 저장 실행 | 원본 대비 화면/소리 증거, 실제 두 플랫폼 실행, 엔진/언어/내보내기 버전 결정 |
| P3 처음부터 끝까지 시험판 | 타이틀→로컬 프로필/로그인 흐름→캐릭터 생성→평민 Lv1→마을→정상 출구→사냥/드롭→거래/장착→Lv5 전직/기초 기술→귀환→저장/종료/재진입. 같은 계정 시험 저장 왕복 가능성도 조기에 확인 | 막히지 않는 하나의 실제 플레이 동선, 오른쪽 4개 패널과 한국어·터치·저장 증거 |
| P4 전체 데이터 일괄 반영 | 확정한 변환기로 지도·NPC·스폰·아이템·기술·음향 등을 한 세대의 실행 패키지로 대량 생성 | 전체 참조/포맷/충돌/시대/조건부 이동 검사, 미연결·보완 목록 |
| P5 전체 시스템·콘텐츠 완성 | 행동 종류별 전투·기술, 4직업 1~99/승급, 상점별 거래/수리, 퀘스트, 죽음/부활, 드롭/내구도. 지역은 연결된 플레이 묶음으로 완성 | 기능별 정상·실패 사례, 각 콘텐츠가 실제 기능을 소비하는 증거 |
| P6 이어하기·설치·업데이트 완성 | 계정 인증/저장 동기화 전체 연결, 오프라인/충돌 처리, 기존 저장 이전, 폰/탭 조작·화면·성능, 서명·버전 보존 | 실제 Windows→Android→Windows 같은 계정 왕복, 업데이트/복구 증거 |
| P7 종합 플레이·최종 대조 | 4직업 자연 성장 검증, 주요·예외 지역/퀘스트, 장시간/강제종료/재연결, 원본 대비 시청각, 깨끗한 설치·업데이트 | 최종 전달 바이너리에서 검증된 결과와 미확인 항목 공개 |

P2에서 만든 PC/Android 빌드를 P3 이후에도 유지한다. Android를 마지막에 처음 열지 않는다. P6은 플랫폼 지원의 시작이 아니라 전체 이어하기와 배포 검증을 완성하는 단계다. P3의 실제 클라우드 왕복이 무료 환경/연결 조건으로 막히면 그 기능만 BLOCKED로 남기고 오프라인 게임 개발을 계속하되 연동 완료라고 표시하지 않는다.

P3에서는 대표 직업으로 일반 진행을 검증하되 네 직업의 생성/전직 분기와 대표 기술 동작 종류도 시험한다. 상위 기술용 테스트 캐릭터는 기능 시험일 뿐 자연 육성 완주의 증거가 아니다. P7의 1~99 및 승급은 실제 검증한 직업/레벨/구간을 정확히 보고한다.

### 5.3 엔진과 재사용

현재의 우선 후보는 새로운 Godot 프로젝트 + 데이터 변환기다. Godot은 Android 내보내기를 지원한다.[S8] 정확한 엔진/언어 버전은 P2의 Windows/Android 동일 장면 결과로 고정한다. 최신이라는 이유만으로 버전을 바꾸거나, 어떤 버전을 쓰면 성능이 해결된다고 미리 약속하지 않는다.

Project1998/RTK는 작동 원리와 데이터 및 재사용 함수의 후보이며, 북미판 엔진을 한국판 정답으로 강제하지 않는다. 기존 프로젝트의 정상 파서·원본 자산·저장 원자적 처리·시험 도구도 평가해 재사용한다. 과거 main.gd 같은 거대한 파일을 통째로 끌고 오지 않는다. 새 아키텍처에 맞는 좁은 모듈만 검증 후 이식한다.

새 구조는 입력/UI, 게임 상태·규칙, 지도/자산 렌더링, 저장·동기화를 분리한다. UI 능력치와 실제 전투 계산은 같은 상태를 읽는다. 지도 지형/출구/스폰/NPC는 데이터로, 기능의 실행은 공통 코드로 처리한다. 퀘스트나 기술 데이터가 요구하는 효과 명령의 지원 여부를 변환 단계에서 검사한다. 조사 원본과 사용자의 저장을 배포 콘텐츠와 섞지 않는다.[S2의 분리 원칙을 참고한 설계 제안]

## 6. 질문 5 — 사전에 고정할 누락 방지·품질 기준

### 6.1 처음 화면부터 종료까지 기능 목록을 먼저 만든다

타이틀/선택 상태/로딩/오류 안내, 아이디·캐릭터 생성/중복/한글 입력/외형, 화면 패널/능력치/아이콘, 이동/방향/가림/충돌/지도/출구, 공격/명중/피격/마력/버프/소리, 레벨/전직/학습/승급, 상점/거래/수리/장비/내구도, 퀘스트/죽음/부활, 저장/재시작/오프라인/계정 전환/업데이트/복구를 모두 한 표에 넣는다.

각 행에는 정상 사례와 실패 사례를 함께 둔다. 예: 구매 성공만 아니라 돈 부족/가방 가득 참/판매 금지/수량 0/취소; 시전 성공만 아니라 미학습/직업·레벨 미달/마력 부족/대상 사라짐/벽/맵 이동 중 시전. 무한 루프·영구 행동 잠김을 검사한다.

### 6.2 기존 치명결함을 새 엔진의 금지 조건으로 등록

| 결함 | 새 구현에서의 필수 조건 |
|---|---|
| 평민 아닌 Lv1·미학습 공격기술 | 신규 생성 상태/희망 직업/실제 직업을 분리. 정상 진행 시험 |
| 북미 지형에 한국 이름만 붙임 | 한국 원본 또는 명시적 재구성 근거. 지명 번역과 지형 복원 판정 분리 |
| 비영사천문 village 고정 | 기술별 규칙+현재 지역/도시+방향 목적지 표. 맵 ID와 안전 좌표를 검증한 뒤 이동 |
| 빈 사냥터를 입구 주위 추정 스폰으로 채움 | 일반/변종/보스 및 스폰 구역/밀도/리스폰 출처 분리. 원작 확인과 사냥 가능 분리 |
| 모든 상점이 공통 전체 재고 사용 | NPC별 재고/서비스 관계를 유지. 근거상 같은 재고는 공유 가능하지만 무차별 대체 금지 |
| 아이콘 누락을 다른 목도 그림으로 대체 | 실패를 식별하고 필수 자산 누락 배포 차단. 원본 이름-그림 대응 시험 |
| 지도 버전만 바뀌면 캐릭터/드롭을 입구로 이동 | 영향 없는 좌표 유지. 명시적 좌표 변환, 불가시 원본/보류 보존. 임의 이동·소실 금지 |
| 필수 맵 누락을 continue로 무시 | 기대한 맵 집합과 로드 집합 대조, 오류 목록 반환, 실패한 후보 배포 차단 |
| 변환 코드 변경 후 오래된 캐시 재사용 | 콘텐츠·파서·컴파일러·설정·타일/팔레트 매핑의 결정적 지문으로 재생성 |
| UI 고치다 게임 규칙 퇴행 | 공통 파일 병렬 덮어쓰기 금지, 좁은 변경과 회귀시험 |

'이동 가능한 칸 찾기'는 안전 처리이지 역사적 위치 복원의 증거가 아니다. 원래 불가능한 지역에 편의 포털을 추가하고 복원 완료라고 하지 않는다. 기본 프로필의 정상 이동은 원본/재구성 규칙으로 연결한다.

### 6.3 시험의 층과 비교 방법

- 자료 전수 자동검사: 해시/파싱/범위/참조/지원 명령/맵 목적지/조건부 도달성/스폰과 출구 충돌.
- 독립 기준 비교: 원본 또는 다른 도구/문서/실제 영상과 비교. 같은 코드로 만든 기대값만으로 자기검증 금지.
- 기능 회귀: 고정 입력 시퀀스·난수 시드·버전으로 전투/거래/성장/저장을 반복. 확률 기능은 한 번의 성공으로 확률 정확성을 판단하지 않음.
- 화면/소리: 같은 지도·방향·장비·배율·조명·행동에서 비교. 새 게임 로그뿐 아니라 프레임과 오디오 증거.
- 네이티브 설치본: Windows EXE, Android 앱, 실제 Galaxy와 에뮬레이터를 구분. Linux 성공을 Windows 성공으로 보고하지 않음.
- 파괴·복구 시험: 맵 1개 삭제/아이콘 범위 오류/캐시 변조/네트워크 차단/동시 저장/업데이트 중 중단. 사용자 실제 원본이 아니라 복사본으로 수행.

지도·기술 수가 크면 전수 자동검사와 전체 썸네일/참조 검사를 하며, 실제 장시간 플레이는 행동 종류·지역군·직업·위험도로 대표/예외를 선정한다. 표본 검사를 전체 수동 완주라고 주장하지 않는다. 실패가 나온 계열은 표본을 확대한다.

### 6.4 성능과 가벼운 실행

목표는 렌더링 60FPS, 최소 30FPS 수준의 안정적인 체감이며 이는 제안 목표이지 현재 측정값이 아니다. P2에서 실제 기기의 시작 시간, 입력 지연, 프레임 시간 p95/p99, 메모리 최고값/증가, 맵 전환, 연속 효과음, 배터리/발열 조건을 측정하고 예산을 고정한다. 애니메이션 원본 속도는 렌더링 FPS와 분리한다.

전체 자료를 보유한다고 전체 맵·모든 PNG를 시작 시 메모리에 올리지 않는다. 현재/인접 맵 및 필요한 그림만 로드하고 메모리 상한이 있는 캐시를 사용한다. 탭 전환·비영사천문·매 프레임마다 원본을 다시 해독하지 않는다. 반복 이동 뒤 메모리 누적과 앱 전환/뒤로가기/통화 후 입력 고착도 검사한다.

### 6.5 저장과 계정 연동

로컬 저장은 임시 기록→검증→원자 교체→직전 백업을 기본으로 한다. 안정 ID, 저장 형식 버전, 콘텐츠/맵 버전, 계정/캐릭터 ID를 분리한다. 이전은 사본에서 한 번만 적용 가능하게 하고 실패 시 양쪽 자료 보존.

같은 계정은 단일 캐릭터의 순차 플레이를 기본으로 한다. 다른 기기의 오래된 저장으로 덮어쓰지 않고, 오프라인 변경은 대기 상태를 유지한다. PC→Android→PC 왕복을 실제 인증/전송 경로로 검사한다. 파일 수동 복사 성공을 계정 동기화 성공으로 대체하지 않는다.

재구축 시험판은 기존 앱·저장과 분리해 공존시킨다. 최종 대체 시 패키지명·서명·버전·저장 이전을 검증한다. 사용자의 기존 앱을 삭제해야만 시험할 수 있는 배포를 기본 경로로 삼지 않는다.

### 6.6 배포·보안·비용

개발 초기에 PC/Android 설치 파일 제작·실행 경로를 확보하고, 이후 같은 입력으로 자동 빌드한다. 실행 바이너리, 콘텐츠, 캐시, 시험 로그에 같은 빌드 지문을 기록한다. 최종 검사 뒤 수정하면 영향 시험을 다시 한다.

출처 불명 EXE를 사용자 주 PC에서 바로 실행하지 않는다. 정적 해제/소스 확인 후 격리 환경을 사용한다. 참고 서버는 로컬 연결로 한정하고 기존 계정 암호·키·세이브를 외부 코드에 제공하지 않는다. 자료 수집이 컴퓨터 감염이나 원본 손상으로 이어져서는 안 된다.

무료 도구라도 실행 인프라·Actions·저장 공간은 별도 비용이 있을 수 있으므로 실행 전 잔여량과 과금 여부를 확인한다. 유료 API·서버·구독·원격 컴퓨터 자동 구매 금지. 비용 불명 단계는 보류하고 가능한 다른 단계는 진행한다.

## 7. 진행·기록·인계

### 7.1 최소 기록 구조

- AGENTS.md: 시작 시 읽을 문서, 현재 승인 범위, 변경 금지 영역.
- docs/rebuild/MASTER_PLAN.md: 이 계획과 요구사항의 정본. 변경 이유/버전을 본문 말미에 누적.
- docs/rebuild/STATE.json: 현재 단계, 승인 여부, 완료/실패/미실행, 다음 행동, 근거 위치.

실제 개발 승인 후 sources/records/evidence 및 자동 생성 카탈로그를 추가한다. 지금 빈 문서 수십 개를 만들지는 않는다.

새 작업자는 AGENTS → MASTER_PLAN → STATE → 실제 원격 HEAD/파일 접근/증거를 확인한다. 이전 전체 조사를 다시 읽는 대신 다음 미해결 항목부터 이어간다. 검증된 파서·이미 처리한 원본은 입력 해시가 같으면 재사용한다. 메모리나 이전 대화 요약만으로 실행 상태를 확정하지 않는다.

자료 담당은 원본/채택 후보/변환 결과를 만들고 게임 담당은 가져오기/상태/기능/실행 검증을 담당한다. 통합 책임자는 한 명으로 고정한다. 자료 담당과 게임 담당이 같은 공통 파일을 동시에 덮어쓰지 않는다. 기능별 변경과 실제 시험 증거를 함께 저장한다.

보고는 '이번 새로 확보/해독/연결/실행 확인한 것, 실패와 미확인, 다음 행동'으로 한다. 중단 시 소스 SHA·콘텐츠 지문·미완료 작업을 기록하고 재개한다. 수행하지 않은 작업을 예약/백그라운드 실행 중이라고 보고하지 않는다.

### 7.2 완료라는 표현의 조건

현재 단계 결과가 있어야 그 단계 완료라고 한다. 필수 기능 미연결·저장 소실·막힌 정상 성장 동선·실제 플랫폼 미실행을 남긴 채 전체 완료라고 하지 않는다. 추론으로 보완한 역사적 요소는 기능 검증을 통과해도 INFERRED를 유지한다. 100% 원작 복원을 미리 약속하지 않는다.

이번 실제 수행: 이전 v2 문서와 주요 로컬 파일 존재 확인, GitHub 브랜치/Project1998 문서 확인, 외부 도구·Godot 공식 문서 조사, 계획 작성과 저장. 새 게임 구현·파서 수정·기준 게임 실행·설치 파일 제작·실기기 검증은 NOT_RUN.

다음 실행 제안: 사용자가 개발/조사 진행을 지시하면 P0/P1의 자료 카탈로그와 부족 항목 우선순위를 먼저 확정하고 P2의 위험 기술 검증으로 이동한다. 이 계획 저장만으로 개발이 시작됐다고 해석하지 않는다.
